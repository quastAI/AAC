# CLAUDE.md

Hierarchical JEPA world models (flat model, HWM, H-JEPA) on Craftax-Classic, planning to diamond. Current phase: the flat model (level 1 alone). `README.md` has the research questions, the flat-model cycle, method and usage; this file has what is needed to work in the repo.

## Layout

- `H-JEPA/` PyTorch: world models (`h_jepa/`), planning and environments (`stable_worldmodel/`), tests (`tests/`). Imported from a fork with `git subtree`.
- `purejaxql/` JAX: PQN-RNN expert and the episode collector (`scripts/collect_craftax_episodes.py`). Also a subtree.
- `analysis/` (numpy, h5py): the package `dataset_section/` (the appendix figures and tables of the dataset section; run from `analysis/`: `python -m dataset_section compute` reads each split as one set, every frame, and writes `dataset_numbers.json`, `plot` makes the figures and tables from that JSON alone (needs matplotlib), `splits` writes the per-split composition tables with a provenance JSON; modules: `data`, `episodes`, `actions`, `spectral`, `change`, `compute`, `tables`, `figures`, `splits`) `compare_runs.py` and `plot_training.py` (loss curves of a run). `experiments/`: `experiments.yaml` (job specs: D1 data plan, D0 = `dataset_section compute`, the flat phase F1-F5 and V1; task sets A offsets, B episode, C chain) and `run.py`. `environment/`: install lists, reference freezes. `notebooks/`: the RunPod notebooks `runpod_dataset.ipynb` (expert, D1, D0, Hub upload), `relabel_dataset.ipynb` (once: the Hub files get the executed actions) and `runpod_flat.ipynb` (the flat-model cycle: smoke run and timing on the real files, F1, F3-F5, V1, runs to the Hub) (see `environment/README.md`, section RunPod). `.github/workflows/tests.yml` is untested and manual-only (`workflow_dispatch`, no automatic runs) (written without runner access).
- The two code folders only share the HDF5 episode file (column table in the README).

**Where to look.** Work in: `H-JEPA/h_jepa/` (world models, training), `H-JEPA/stable_worldmodel/` (planning, environments), `purejaxql/` (expert, collector), `analysis/dataset_section/` (dataset appendix), `experiments/` (jobs). Leave alone unless asked, and exclude from searches: `data/` (9 GB, never read the HDF5 files directly: go through `dataset_section`), `Craftax/` and `stable-worldmodel-craftax/` (read-only reference clones, gitignored, never edit), `papers/` (PDFs, gitignored), `reports/` (generated: rerun the commands instead of editing). ## Contracts that must not drift

- **Actions:** `action` is the action the game executed (noop while asleep: `craftax_step` replaces every action then), `action_policy` the policy's choice; the rule is `executed_actions` in the collector, used by the collector, `relabel_asleep.py`, `check_replay.py` (and mirrored by `dataset_section`'s `Split.executed_action`). Training, IDM and planning use `action`.
- **Episodes** are replayable from `seed` + actions (`action` or `action_policy`, identically): `reset_key, step_key, _ = split(PRNGKey(seed), 3)`, step at `state.timestep == t` uses `fold_in(step_key, t)`. The collector (`purejaxql`) and the env (`H-JEPA/stable_worldmodel/envs/craftax/env.py`) both follow it; `H-JEPA/tests/data/craftax_classic_episode.npz` guards it. `World` resets envs with the dataset's `seed` column.
- `full_state` is a flat uint8 snapshot of the Craftax state pytree (leaf order), made by `pack_state` in the collector and the env. Craftax stays pinned at 1.6.1.
- Env: `terminated` = goal success, death/horizon = `truncated`; the env freezes after death or the horizon (after goal success it keeps stepping; `World` ORs the success flags).
- Discrete actions: level-1 one-hot (`level1.wm.num_actions`); the normalizer artifact has no action stats and records `num_actions`. Upper levels: `VQActionEncoder` (groups x codes, optional duration k); planners read `model.get_action_spec()`.
- `CategoricalCEMSolver` mirrors `GradientSolver` (`configure(..., level=)`, `solve`, `solve_records`). Its duration slot is pinned to the default stride unless `allowed_durations` says otherwise.

## Decisions taken

Settled with the user: goal test `new_achievements` with all achievements counting (random baseline as reference); protocol A main task set = offsets with progress, per offset; data = final expert (diamond filter) + rollouts of earlier snapshots of the expert's training (see 2026-10-16 below), seed ranges 0 / 1M / 2M for train / val / test, headline runs use the test worlds; level-1 step = 1 environment step. Earlier: Discrete CEM at every level; VQ latent actions with a factorized codebook above level 1; IDM (cross-entropy) on at every level (ablated per model later); native 63x63 frames with a ViT of patch 7; actors are learned separately later (frozen, after the world model); the band of horizons is meant to become the default. Planner design (proposals, trust region, actors) is deferred; README "Open decisions" lists the rest.

Settled on 2026-10-13 (review session): tasks and all planning evaluation come from diamond-reaching expert episodes only (`source == 0`); all achievements count, no per-group extras for now; horizons are fixed over the episode (`horizon_schedule: fixed`); strides and depth come from the dataset section so that the top level comfortably spans the expert's typical time to diamond (a quantile, for example the 75th); the flat model (called LeWM until 2026-10-20) is just the hierarchy with one level, so the depth is a setting (1 to 4), the first trained model is the level-1-only one and a random baseline runs on the same tasks; the data mix (shares counted in frames) is decided after the data exists and its behaviour has been analysed; episodes of sources noised (1) and early (3), which may die, stay in the loss of every level, without an ablation, and uniform random episodes (2), if any, train level 1 only; upper-level CEM starts from code sequences of the training data (actors replace that later); the terminal (death) frame is padded for the level steps. Death and starvation beyond that (a learned survival head, longer top-level clips) are left open until the data is analysed.

Settled on 2026-10-16 (D0 redesign, the script was removed on 2026-10-20, see below): D0 reported facts and makes no stride or depth choice. Headline: the entity frequency gap of the paper on the 7 probe entities of `probe_eval.py` (Welch window 256, sensitivity 64/128/512, an episode bootstrap, the same estimator for the view and terrain from the `state` column as extras); an entity whose power sits in the two lowest bins is `limited` by the window (staircases, walks, the day) and the gap is then a lower bound. The threshold 2x is the paper's boundary between six environments, a heuristic; a large gap is near certain here, so the information is in the ladder. The ladder clusters entities by the median time between their events (the spectral period cannot order the slow end), reports a stride candidate (median) and a band candidate (p10 to p90, CV as irregularity) per cluster, and the clips left at the band's top; later experiments decide the strides. Spectra, events and tasks use the expert episodes; the gap is also given per source and snapshot and for the placeholder mix. Thresholds that are heuristics: gap 2x, cluster ratio 2x, CV 0.5 / 1, critical frames (food, drink or energy at most 2, or health at most 3). Checks against the environment's own clocks (food 26, drink 21, energy 31, the day 300) print WARNING when the columns or events are wrong. Dropped: the stride-tuple enumeration and the level-1 step item.

Settled on 2026-10-19 (dataset first): the experiment table (E1-E8) was removed from the README. Experiments are not planned yet: first the dataset is understood (descriptive figures and tables, without experiment framing; the plan was in `analysis/README.md`, removed on the same day, see git history), then the flat baseline, then step by step. (The E-ids and C1 drafts were replaced on 2026-10-20, see below.)

Settled on 2026-10-20 (dataset section): the appendix figures and tables are the package `analysis/dataset_section/`, independent of the D0 script, which was removed with its ladder, task, survival and per-source sections (git history has them). Each split is one set with every frame (train as a whole, not chunks; the old `Data` class sampled every second episode above 2M frames). Content (one figure or table per topic, the redundant ones were dropped): episode length weighted by frames (train and test) and time to the diamond (test), the entity frequency gap (test only, the pure expert; a number in the JSON for one sentence in the text), the first-unlock ladder (figure and table), the change matrix (net change per state component and lag 1 to 800, view pooled, world-frame terrain and mobs up to lag 6), clips per stride, overlapping and independent as two figures (clips depend on context + rollout only; overlapping clips at a high stride are phase-shifted copies of the same trajectory with nearly the same slow state), action coverage split into succeeded, failed and asleep steps (17% of the steps are taken while asleep and are ignored by the game, most of the failed-looking crafting presses among them), and chunk information. Validation is only compared with train (distances in the JSON). The `D0` experiment id stays and runs `dataset_section compute`.

Settled on 2026-10-20 (flat model phase): the first deliverable is a strong flat model (level 1 alone, no longer called LeWM; the upstream `*_lewm.yaml` configs of the other benchmarks keep the paper's name). Every variant runs the same cycle: train, probes (encoded latents and open-loop predicted latents at k = 1, 2, 4, ..., 64; probes fitted on encoded latents of the train worlds and applied unchanged to the predictions on the validation worlds, against copy-last-latent and the untrained control; successful crafts and placements split from failed presses, IDM accuracy per action class), then planning P1 fixed-offset goals (protocol A), P2 diamond through oracle subgoals (the expert's frames at multiples of the goal offset in the same world, switched after a fixed budget per subgoal, placeholder 2x the offset; the last subgoal is the diamond frame and keeps the rest of the budget), P3 diamond from the final goal only (protocol B), each with the random baseline and example videos (GIF via Pillow, 4x upscaled, real frame next to the goal frame with step and unlocks, the first 8 tasks of a run). The goal offset, the planning horizon and the CEM settings are set once on the default model (validation worlds) and then frozen for every variant; how they are searched is not planned (no full sweep, decided when the default model exists). Default model: `craftax_hjepa num_levels=1`, history 3, `rollout_n` 1, CLS latent, IDM on (no IDM ablation). Variants, one at a time against the current best: context and rollout loss; SIGReg and IDM coefficients (no sweep, changed from loss curves, probes and planning); delta prediction (residual on the last latent, same loss) only if the default barely beats copy-last-latent or static entities drift; CLS vs patch tokens last, only if the rollout probes show CLS losing fast entities. No seed-noise run: one seed per variant. Probe targets gain the material counts in view, the material of the facing tile and the sleeping flag (from `state`). The dataset is fixed, except that the actions taken while asleep (17% of the steps) are relabeled as noop, the action the game executed (asleep steps only, not failed presses; decided 2026-10-21: the IDM can learn it from the frame, sleep is drawn grey with the sleeping sprite, unlike night; it also keeps the later VQ codes of sleeping chunks consistent); the dataset section counts them as noop; oversampling rare transitions (successful crafts about 0.1% of steps, clips uniform over frames) waits for the event split of the default model's probes.

Settled on 2026-10-23 (first pod session): F1 and the variants train 10 epochs (155k steps, 16.6 min per epoch, 2.8 A100-hours, measured with `time_run.py`; the schedule is tied to `max_epochs`); the end-of-training probe is the F1/V1 probe (`health.probe_clips` 512, the `probe` jobs of `run.py` only run if it failed); two critical epochs in a row stop a training (`health.stop_after_critical_epochs`, the model is saved); the latent scale (mean std outside 0.3-3 with SIGReg) is a finding (`REP_SCALE`); the drift horizon is 10 (the planning horizon); the live health metrics run every 2000 steps (`health.live_every`), Lightning logs every 250 steps (`trainer.log_every_n_steps`, default 50) and stable-pretraining's folder and the notebook's logs are on the pod's local disk (`spt_dir`): with the defaults every logging step froze the A100 run for about 10 s (the main thread waited in the FUSE layer of the network volume), 3.5 it/s instead of 13 it/s = 20 minutes per epoch, 3.3 hours for 10 epochs; the epoch-end evaluation, which the stop rule uses, is separate. Planning costs more than training (README, Compute): the solver `batch_size` (5) and the task sets are part of F2.

## Diagnostics (all in `H-JEPA/h_jepa`)

`probe_eval.py` probes every level and, at level 1, rollouts (`--horizons`, history = `health.plan_history`), the place/make events (`shown`: predicted success-minus-failure gap of the inventory probe over the encoded gap) and the IDM per action; the `state` targets need the `state` column in both files; `--checkpoint` and `--out` probe an epoch checkpoint without writing `health/probe_report.md` (the output of the probe jobs in `run.py`). `health.py` holds the metric functions, the `Thresholds` (heuristics, to be tuned on real runs) and `diagnose_training/planning/probing` returning `Finding`s (critical/warn/info with a hint). `training_monitor.py` (callback: live, per epoch, end report, optional probing), `planning_video.py` (GIFs of the first `eval.videos` tasks through `World.evaluate_from_dataset(recorder=)`; long budgets subsampled to `video_max_frames`, unlocks and the end kept), `planning_metrics.py` (`RecordingPolicy`, `RecordingSolver`, `RandomRecordingPolicy`, `summarize_planning`), `probe_eval.py`, `eval_tasks.py`, `time_run.py`, `cpu_threads.py` (torch threads from the container's CPU quota). `analysis/plot_training.py` draws the loss curves and health metrics of a run from its metrics CSV. The goal test is `new_achievements` (progress-defined); tasks have one world seed each. A random-policy baseline on the same tasks is needed to read any planning number.

## Configs

One training config per model type (`craftax_hjepa`, `craftax_hwm`) and one planning config (`craftax_plan`) serve every depth: `num_levels=1..4` and `levelN.stride=..` are settings (level 1 alone is the flat model). The blocks of levels above `num_levels` stay in the config and are ignored (`data.dataset_kwargs` for the dataset, `_drop_levels_above_model` for planning). In `craftax_plan` the top level plans its own `horizon`; a level below plans one upper step, so its horizon is the stride of the level above (`horizon_schedule: fixed`).

## Pitfalls seen

- The expert checkpoint must contain BatchRenorm `batch_stats` (the training script saves them now); older checkpoints cannot be used.
- A level that follows the plan of the one above must have a horizon in [stride, 2 x stride) with one subgoal (`check_subgoal_horizon` raises otherwise); `craftax_plan` derives it from the stride. The Craftax eval configs use `horizon_schedule: fixed` (the Push-T `decreasing` default shrinks the horizon over the budget and skips upper levels late). `receding_horizon` counts level-1 steps.
- The planning evaluation at the end of training is off for Craftax (`planning_eval.enabled: false` in `base/craftax.yaml`): `craftax_plan` has no task file, so it would fail when training ends; planning runs as F3-F5. `time_run.py --loader-batches N` times the real training loader (the pixels are gzip in chunks of 100 frames).
- Evaluation needs a task file (`eval_tasks.py`) passed as `load_eval_trajs_path`; `eval.chunk_size` must be null without it. `output.dir` is relative to the parent of the policy directory (or absolute for `policy=random`).
- P2 (`eval_tasks.py --mode chain`) switches only the planner's goal frame (`goal_schedule` in the payload, `_switch_goals` in `World`); the env's goal test stays the final goal. The infos of the reset carry no goal test yet (`goal_required` 0 before the first step), with or without subgoals.
- Tasks are one per world seed (the evaluation asserts distinct seeds). Random agents solve some tasks (wake_up, drink, sapling): always compare with the random baseline. Smoke runs on untrained models only check plumbing.
- The training probes at its end and writes `health/probe_report.md`, the output of the `probe` jobs in `run.py`, which are then skipped: `health.probe_clips` (512) sets the clip count, a repeat needs the report deleted (`run.py --force` repeats every job of the experiment, the training included).
- RunPod pod (first flat-model session): the network volume `/workspace` refuses `chmod` and file times (`Operation not permitted`): `git clone` and `venv`/`pip` fail on it, the Hub download and stable-pretraining's `environment.json` dump only warn or log a harmless traceback. The flat notebook therefore keeps the clone (`/root/AAC`), the venv, the episode files (`/root/data`), its logs (`/root/logs`) and stable-pretraining's folder (`spt_dir=/root/spt`, `<run>/spt` links to it) on the local disk and links `ckpts`, `reports` and `eval_tasks` back to the volume. Anything written often must stay off the volume: at every logging step the training stalled about 10 s there (`cat /proc/<pid>/wchan` showed `request_wait_answer`); only `lightning_resume/last.ckpt` (every 2000 steps, about 10 s) and the models are written to it. Reading the training file from the volume stalled the dataset build (more than 4 minutes, 2 seconds on local disk).
- The container may use fewer CPUs than `nproc` shows (13.6 of 128: `cat /sys/fs/cgroup/cpu.max`). torch's 128 threads throttled each other (a 16-clip probe took 490 s, 12 s with 8 threads): `cpu_threads.limit_threads()` runs in the entry points and the notebook sets `OMP_NUM_THREADS`; the 12 loader workers share the same quota. The Jupyter kernel's `MPLBACKEND` (`matplotlib_inline`) does not exist in the venv: the notebook sets `agg`.
- `py-spy` cannot attach inside the container (no ptrace); profile with `timeout -s INT 240 python -m cProfile -o out.prof ...` (the interrupt still writes the profile), then `pstats`. `sh(quiet=True)` in the notebook shows only the tail of a failing run, which can be one harmless traceback: `log=` keeps all of it in `LOGS/<log>.log`.
- The metrics CSV of a run is `spt/runs/<date>/<time>/<id>/metrics.csv` (stable-pretraining's logger, flushed every 100 logged steps), not `lightning_logs/`; `analysis/plot_training.py` reads it.
- Probe scores below zero mean too few samples for the latent dimension (`PROBE_FEW_SAMPLES`).
- Shell: zsh does not split unquoted variables; `timeout` is missing; `sleep` loops in the foreground are blocked, use `until ...; do sleep 5; done` as a background command; the safety check rejects `zsh -c "..."` wrappers, write a script file instead.
- A file collected before 2026-10-21 has no `action_policy` (the policy's choice in `action`): the collector refuses to append to it (column mismatch) until `relabel_asleep.py` has run; the flat notebook refuses to train on it.
- Collection: the collector appends and `--target-frames` counts the frames of one run, so a repeated run adds a full share on new seeds. `run.py` writes a marker `$HJEPA_HOME/collect_done/<job>` after each finished collect job (local and SLURM) and skips those; a killed run has none and starts again (its partial episodes stay).
- Expert training overrides need the `alg.` prefix on the command line (`alg.SAVE_PATH=...`, `alg.RESUME=true`): the group file's own value beats a top-level `SAVE_PATH=...`, which is silently ignored.
- Expert training: the chunked loop (`chunk_fn` in `pqn_rnn_craftax.py`) must keep the greedy test a real `lax.cond`: under `vmap` the state arrives batched, the cond becomes a select and the 10000-step test runs in every update (fixed for one seed, several seeds still do it; a test guards it). Time the expert with `purejaxql/scripts/time_expert.py` before choosing `TOTAL_TIMESTEPS`: the run length also sets the learning-rate and epsilon schedules and cannot be extended later.
- RunPod: the image's `LD_LIBRARY_PATH=/usr/local/cuda/lib64` (CUDA 12.8) makes JAX segfault at the first matmul next to the pip CUDA 12.9 libraries; run JAX without it (the notebook strips it). Seen on a pod with Python 3.12.
- GPU: `purejaxql[jax_envs]` alone installs the CPU jax on Linux; use `environment/jax-gpu-requirements.txt` (`jax[cuda12]==0.4.38`). Episodes collected on a GPU must pass `purejaxql/scripts/check_replay.py` on the CPU before anything is trained or planned on them. Never run the JAX tests with the python of `Craftax/.venv` (jax 0.11).
- `hjepa_forward` logs only metrics whose key contains `loss`, which is why some statistics are named `*_loss_levelN`.
