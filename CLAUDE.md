# CLAUDE.md

Hierarchical JEPA world models (flat model, HWM, H-JEPA) on Craftax-Classic, planning to diamond. Current phase: the flat model (level 1 alone). `README.md` has the research questions, the flat-model cycle, method and usage; this file has what is needed to work in the repo.

## Layout

- `H-JEPA/` PyTorch: world models (`h_jepa/`), planning and environments (`stable_worldmodel/`), tests (`tests/`). Imported from a fork with `git subtree`.
- `purejaxql/` JAX: PQN-RNN expert and the episode collector (`scripts/collect_craftax_episodes.py`). Also a subtree.
- `analysis/` (numpy, h5py): the package `dataset_section/` (the appendix figures and tables of the dataset section; run from `analysis/`: `python -m dataset_section compute` reads each split as one set, every frame, and writes `dataset_numbers.json`, `plot` makes the figures and tables from that JSON alone (needs matplotlib), `splits` writes the per-split composition tables with a provenance JSON; modules: `data`, `episodes`, `actions`, `spectral`, `change`, `compute`, `tables`, `figures`, `splits`) `compare_runs.py` and `plot_training.py` (loss curves of a run). `experiments/`: `experiments.yaml` (job specs: D1 data plan, D0 = `dataset_section compute`, the flat phase F1-F5, the variants V1 and the ablation A1; task sets A offsets, B episode, C chain) and `run.py`. `environment/`: install lists, reference freezes. `notebooks/`: the RunPod notebooks `runpod_dataset.ipynb` (expert, D1, D0, Hub upload), `relabel_dataset.ipynb` (once: the Hub files get the executed actions), `runpod_flat.ipynb` (the flat model: smoke run and timing on the real files, F1 and its probe suite, F3 = the cheap P1 that the variants compare with, F4-F5 later, runs to the Hub), `runpod_bc_entities.ipynb` (only the entity analysis of `bc.py`, see Diagnostics) and one notebook per variant, `runpod_<EXPERIMENT>_<RUN>.ipynb` (F1 from the Hub, a smoke run, `run.py run <EXPERIMENT> --run <RUN>`, upload; identical apart from the title and the configuration cell, which a test checks, and a test asks for one per trained run of a `V` or `A` experiment); their helpers are `pod.py` (see `environment/README.md`, section RunPod). `.github/workflows/tests.yml` is untested and manual-only (`workflow_dispatch`, no automatic runs) (written without runner access).

## Contracts that must not drift

- **Actions:** `action` is the action the game executed (noop while asleep: `craftax_step` replaces every action then), `action_policy` the policy's choice; the rule is `executed_actions` in the collector, used by the collector, `relabel_asleep.py`, `check_replay.py` (and mirrored by `dataset_section`'s `Split.executed_action`). Training, IDM and planning use `action`.
- **Episodes** are replayable from `seed` + actions (`action` or `action_policy`, identically): `reset_key, step_key, _ = split(PRNGKey(seed), 3)`, step at `state.timestep == t` uses `fold_in(step_key, t)`. The collector (`purejaxql`) and the env (`H-JEPA/stable_worldmodel/envs/craftax/env.py`) both follow it; `H-JEPA/tests/data/craftax_classic_episode.npz` guards it. `World` resets envs with the dataset's `seed` column.
- `full_state` is a flat uint8 snapshot of the Craftax state pytree (leaf order), made by `pack_state` in the collector and the env. Craftax stays pinned at 1.6.1.
- Env: `terminated` = goal success, death/horizon = `truncated`; the env freezes after death or the horizon (after goal success it keeps stepping; `World` ORs the success flags).
- Discrete actions: level-1 one-hot (`level1.wm.num_actions`); the normalizer artifact has no action stats and records `num_actions`. Upper levels: `VQActionEncoder` (groups x codes, optional duration k); planners read `model.get_action_spec()`.
- `CategoricalCEMSolver` mirrors `GradientSolver` (`configure(..., level=)`, `solve`, `solve_records`). Its duration slot is pinned to the default stride unless `allowed_durations` says otherwise.

## Decisions taken

Settled with the user: goal test `new_achievements` with all achievements counting (random baseline as reference); protocol A main task set = offsets with progress, per offset; data = final expert (diamond filter) + rollouts of earlier snapshots of the expert's training (see 2026-10-16 below), seed ranges 0 / 1M / 2M for train / val / test, headline runs use the test worlds; level-1 step = 1 environment step. Earlier: Discrete CEM at every level; VQ latent actions with a factorized codebook above level 1; IDM (cross-entropy) on at every level (ablated per model later); native 63x63 frames with a ViT of patch 7; actors are learned separately later (frozen, after the world model); the band of horizons is meant to become the default. Planner design (proposals, trust region, actors) is deferred; README "Open decisions" lists the rest.

Settled on 2026-10-13 (review session): tasks and all planning evaluation come from diamond-reaching expert episodes only (`source == 0`); all achievements count, no per-group extras for now; horizons are fixed over the episode (`horizon_schedule: fixed`); strides and depth come from the dataset section so that the top level comfortably spans the expert's typical time to diamond (a quantile, for example the 75th); the flat model (called LeWM until 2026-10-20) is just the hierarchy with one level, so the depth is a setting (1 to 4), the first trained model is the level-1-only one and a random baseline runs on the same tasks; the data mix (shares counted in frames) is decided after the data exists and its behaviour has been analysed; episodes of sources noised (1) and early (3), which may die, stay in the loss of every level, without an ablation, and uniform random episodes (2), if any, train level 1 only; upper-level CEM starts from code sequences of the training data (actors replace that later); the terminal (death) frame is padded for the level steps. Death and starvation beyond that (a learned survival head, longer top-level clips) are left open until the data is analysed.

Settled on 2026-10-16 (D0 redesign, the script was removed on 2026-10-20, see below): D0 reported facts and makes no stride or depth choice. Headline: the entity frequency gap of the paper on the 7 probe entities of `probe_eval.py` (Welch window 256, sensitivity 64/128/512, an episode bootstrap, the same estimator for the view and terrain from the `state` column as extras); an entity whose power sits in the two lowest bins is `limited` by the window (staircases, walks, the day) and the gap is then a lower bound. The threshold 2x is the paper's boundary between six environments, a heuristic; a large gap is near certain here, so the information is in the ladder. The ladder clusters entities by the median time between their events (the spectral period cannot order the slow end), reports a stride candidate (median) and a band candidate (p10 to p90, CV as irregularity) per cluster, and the clips left at the band's top; later experiments decide the strides. Spectra, events and tasks use the expert episodes; the gap is also given per source and snapshot and for the placeholder mix. Thresholds that are heuristics: gap 2x, cluster ratio 2x, CV 0.5 / 1, critical frames (food, drink or energy at most 2, or health at most 3). Checks against the environment's own clocks (food 26, drink 21, energy 31, the day 300) print WARNING when the columns or events are wrong. Dropped: the stride-tuple enumeration and the level-1 step item.

Settled on 2026-10-20 (flat model phase): the first deliverable is a strong flat model (level 1 alone, no longer called LeWM; the upstream `*_lewm.yaml` configs of the other benchmarks keep the paper's name). Every variant runs the same cycle: train, probes (encoded latents and open-loop predicted latents at k = 1, 2, 4, ..., 64; probes fitted on encoded latents of the train worlds and applied unchanged to the predictions on the validation worlds, against copy-last-latent and the untrained control; successful crafts and placements split from failed presses, IDM accuracy per action class), then planning P1 fixed-offset goals (protocol A), P2 diamond through oracle subgoals (the expert's frames at multiples of the goal offset in the same world, switched after a fixed budget per subgoal, placeholder 2x the offset; the last subgoal is the diamond frame and keeps the rest of the budget), P3 diamond from the final goal only (protocol B), each with the random baseline and example videos (GIF via Pillow, 4x upscaled, real frame next to the goal frame with step and unlocks, the first 8 tasks of a run). The goal offset, the planning horizon and the CEM settings are set once on the default model (validation worlds) and then frozen for every variant; how they are searched is not planned (no full sweep, decided when the default model exists). Default model: `craftax_hjepa num_levels=1`, history 3, `rollout_n` 1, CLS latent, IDM on (no IDM ablation). Variants, one at a time against the current best: context and rollout loss; SIGReg and IDM coefficients (no sweep, changed from loss curves, probes and planning); delta prediction (residual on the last latent, same loss) only if the default barely beats copy-last-latent or static entities drift; CLS vs patch tokens last, only if the rollout probes show CLS losing fast entities. No seed-noise run: one seed per variant. Probe targets gain the material counts in view, the material of the facing tile and the sleeping flag (from `state`). The dataset is fixed, except that the actions taken while asleep (17% of the steps) are relabeled as noop, the action the game executed (asleep steps only, not failed presses; decided 2026-10-21: the IDM can learn it from the frame, sleep is drawn grey with the sleeping sprite, unlike night; it also keeps the later VQ codes of sleeping chunks consistent); the dataset section counts them as noop; oversampling rare transitions (successful crafts about 0.1% of steps, clips uniform over frames) waited for the event split of the default model's probes and is now the ablation A1 (2026-10-27, below), not a model setting.

Settled on 2026-10-23 (first pod session): F1 and the variants train 10 epochs (155k steps, 16.6 min per epoch, 2.8 A100-hours, measured with `time_run.py`; the schedule is tied to `max_epochs`); the end-of-training probe is the F1/V1 probe (`health.probe_clips` 512, the `probe` jobs of `run.py` only run if it failed); two critical epochs in a row stop a training (`health.stop_after_critical_epochs`, the model is saved); the latent scale (mean std outside 0.3-3 with SIGReg) is a finding (`REP_SCALE`); the drift horizon is 10 (the planning horizon); the live health metrics run every 2000 steps (`health.live_every`), Lightning logs every 250 steps (`trainer.log_every_n_steps`, default 50) and stable-pretraining's folder and the notebook's logs are on the pod's local disk (`spt_dir`): with the defaults every logging step froze the A100 run for about 10 s (the main thread waited in the FUSE layer of the network volume), 3.5 it/s instead of 13 it/s = 20 minutes per epoch, 3.3 hours for 10 epochs; the epoch-end evaluation, which the stop rule uses, is separate. Planning costs more than training (README, Compute): the solver `batch_size` (5) and the task sets are part of F2.

Settled on 2026-10-25 (probe suite): the probes are one after-training eval, the probe suite (`probe_suite.py`, package `probing/`), which replaced `probe_eval.py` and `tile_probe.py` (git history has them); it runs on the final model only (no epoch probes; F1, probed before it existed, gets it from a notebook cell). Every entity (block types, mobs, inventory items, vitals, facing, sleeping, daylight, achievements) is followed along one chain: pixels (the ceiling) -> ViT patch tokens (layers 3, 6, 9, last; untrained ViT as control) -> CLS before the projector -> latent (linear and MLP, untrained latent as control) -> sprite swap -> one step (events incl. collecting, mob motion) -> rollout; the verdict is the first link that fails (heuristics: a stage keeps under 80% of the best stage before it, a later link under 0.5, a pixel ceiling under 0.2). Why a tile is lost: rarity vs look-alike sprites (rank correlations), the spectrum (top-k principal components), loss attribution (which transitions carry the one-step loss). Rollouts are scored by the change test (only where the entity changed; copy is wrong there by construction; unchanged windows apart), history 1 and 3. Absolute position is no target (egocentric frames), mobs are scored as presence, tiles per position with a 7x9 map decoder. Disjoint clips, intervals from an episode bootstrap. The cost-landscape block (expert vs alternative action sequences, predicted vs realized cost) is out: planning measures it; the model-only distance checks stay (what the latent distance sees, the distance to a goal along the expert path). Whether capacity or the objective drops an entity needs a training run (an auxiliary map decoder on the latent): the last step, only when needed.

Ablation A1, run first and kept apart from the model variants (id `A`, not `V`): F1 with balanced clip sampling (`balance.py`, `data.balance.*`, `flat_balanced`), SIGReg unchanged at 0.09. It is an ablation only, never a model candidate: the weights come from simulator labels (`state`: the faced block; `inventory` and `vitals`: the events) that a real agent would not have, and the main models must not rely on such data. It asks whether the loss of rare faced tiles and rare events in the latent is a matter of frequency. Weighting: a clip holds the faced block of its frames and the successful events of its transitions (the probe suite's event table); an item below 5% of the clips is lifted toward 5%, at most 8 times (the cap), and only if it comes from at least 500 scenes (runs of consecutive clips): the transitions are few (a diamond is collected about once per episode, 1,800 times in the training data), and more draws would be memorising. Draws per epoch and the schedule are unchanged; the clip weight is the largest of its items. The numbers are heuristics (cap 8, share 5%, 500 scenes), chosen from the counts of the training split before the run: cap 4 lifted diamond only about 3 times (0.42% to 1.3% of the draws), 8 gives 2.3% (collecting diamond 1.5%) with 0.99M effective clips of 1.99M and about 240 draws per diamond-collect scene in 10 epochs (30 natural), 16 would leave a third of the effective clips; faced iron and coal reach 5% under any cap, only the share target moves them (7% at 10%); overfitting is watched in the probes (fit on train clips, scored on validation clips) and the IDM and validation curves against F1 (`balance.json` of the run has every item before and after). Judged on the natural validation and probe distribution, by the probes and the cheap P1, not by the loss (not comparable with F1's). Settled on 2026-10-28 (ablation A2, after the F1 probe suite with its additions and A1): the run `flat_map_decoder` of experiment A2 (first filed as V1c, moved because its labels come from the simulator: an ablation like A1, never a model candidate; notebook `runpod_A2_flat_map_decoder.ipynb`, reports `A2_flat_map_decoder_*`). Settled on 2026-10-31 (slowness analysis of F1, analysis only: no loss, no sampler change): the hypothesis was that SIGReg takes its batch variance from cheap slow factors (episode identity, inventory, daylight) and lets fast ones go. `slowness/` (package in `H-JEPA/h_jepa`, tests `H-JEPA/tests/test_slowness.py`) measures it on the epoch checkpoints 1, 2, 5, 10 and an untrained control, on one nested sample of the validation file (211 episodes of at least 256 frames x 4 windows spread over each episode x 64 consecutive frames; `encode` stores CLS token and latent once, `report` is a rerun of everything). The training sampler (more clips of one episode or window per batch, E x K or windows) was considered and left out for now: this phase is about understanding. One seed, F1 only, heuristic thresholds in `report.THRESHOLDS`. Measured: the variance of the F1 latent is mid-scale and not episode identity (episode share 0.19 against a null of 0.15, untrained 0.13 against 0.13; between windows of an episode 0.41, within a window 0.38, within a 4-frame clip 0.02, down from 0.04 untrained); effective rank 103 of 192 and 101 after centering per episode, rising over training; SIGReg of 8 episodes x 16 frames from one window is 6.6x its iid value, the whole game state whitened would give 2.5x (the latent is slower than the state, the gap is moderate, not an order of magnitude); inventory, achievements and daylight alone explain 0.29 of the latent's variance (CLS token 0.51), the view composition, the neighbouring tiles and facing about nothing; mobs, ores and lava in view lose their linear read (cow 0.59 untrained to 0.03, iron 0.65 to 0.03, skeleton 0.43 to 0.03), the expensive ones (arrow, skeleton, cow, zombie: cost 0.17 to 0.46) and the rare ones (ores, lava: change in under 5% of the steps) alike, and a one-layer MLP does not read them either (rare targets overfit: lower bounds); the predictor's one-step error is 0.007 of the variance, 99% of the variance lies on axes where the error is under 5% of it, and shuffled actions raise the error to 1.5 times copying: the prediction loss exerts little pressure on the final latent, the selection happened before epoch 1 ended. Not settled: whether expensive or rare is what removes a factor (both are lost; the two are confounded in this data), and the rate at which the factors go during the first epoch (no checkpoint before epoch 1). Caveats: regressing the latent on the 1,323-dimensional view map overfits (negative held-out R^2), so `view` (counts) and `near` (the four neighbouring tiles) replaced it; the null of the episode share deals whole windows to random episodes (rough); the sample is uniform over episodes, not over frames, and mixes sources 0 and 3; the whitened-state reference is one choice of what a complete latent looks like. Features: `data/slowness/F1_flat_seed42/` (gitignored), report: `reports/slowness_F1/`.

## Configs

One training config per model type (`craftax_hjepa`, `craftax_hwm`) and one planning config (`craftax_plan`) serve every depth: `num_levels=1..4` and `levelN.stride=..` are settings (level 1 alone is the flat model). The blocks of levels above `num_levels` stay in the config and are ignored (`data.dataset_kwargs` for the dataset, `_drop_levels_above_model` for planning). In `craftax_plan` the top level plans its own `horizon`; a level below plans one upper step, so its horizon is the stride of the level above (`horizon_schedule: fixed`).

## Pitfalls seen

- The expert checkpoint must contain BatchRenorm `batch_stats` (the training script saves them now); older checkpoints cannot be used.
- A level that follows the plan of the one above must have a horizon in [stride, 2 x stride) with one subgoal (`check_subgoal_horizon` raises otherwise); `craftax_plan` derives it from the stride. The Craftax eval configs use `horizon_schedule: fixed` (the Push-T `decreasing` default shrinks the horizon over the budget and skips upper levels late). `receding_horizon` counts level-1 steps.
- The planning evaluation at the end of training is off for Craftax (`planning_eval.enabled: false` in `base/craftax.yaml`): `craftax_plan` has no task file, so it would fail when training ends; planning runs as F3-F5. `time_run.py --loader-batches N` times the real training loader (the pixels are gzip in chunks of 100 frames).
- Evaluation needs a task file (`eval_tasks.py`) passed as `load_eval_trajs_path`; `eval.chunk_size` must be null without it. `output.dir` is relative to the parent of the policy directory (or absolute for `policy=random`).
- P2 (`eval_tasks.py --mode chain`) switches only the planner's goal frame (`goal_schedule` in the payload, `_switch_goals` in `World`); the env's goal test stays the final goal. The infos of the reset carry no goal test yet (`goal_required` 0 before the first step), with or without subgoals.
- Tasks are one per world seed (the evaluation asserts distinct seeds). Random agents solve some tasks (wake_up, drink, sapling): always compare with the random baseline. Smoke runs on untrained models only check plumbing.
- The training runs the probe suite at its end (781 s on an A100 for F1 with 512 clips per split, before the additions of 2026-10-27, which add trained probes) and writes `health/probe_report.md`, the output of the `probe` jobs in `run.py`, which are then skipped: `health.probe_clips` (512 disjoint clips per split) sets the clip count, a repeat needs the report deleted (`run.py --force` repeats every job of the experiment, the training included).
- RunPod pod (first flat-model session): the network volume `/workspace` refuses `chmod` and file times (`Operation not permitted`): `git clone` and `venv`/`pip` fail on it, the Hub download and stable-pretraining's `environment.json` dump only warn or log a harmless traceback. The flat notebook therefore keeps the clone (`/root/AAC`), the venv, the episode files (`/root/data`), its logs (`/root/logs`) and stable-pretraining's folder (`spt_dir=/root/spt`; the run folder's `spt_location.txt` names it) on the local disk and links `ckpts`, `reports` and `eval_tasks` back to the volume. Anything written often must stay off the volume: at every logging step the training stalled about 10 s there (`cat /proc/<pid>/wchan` showed `request_wait_answer`); only `lightning_resume/last.ckpt` (every 2000 steps, about 10 s) and the models are written to it. Reading the training file from the volume stalled the dataset build (more than 4 minutes, 2 seconds on local disk).
- Files written to the network volume shortly before a pod stop can be missing on the next pod (seen once: the stop came 2 to 10 minutes after the last writes; `last.ckpt` of 10 minutes before survived, the later `last.ckpt` writes, the epoch's `flat_epoch_N_object.ckpt`, a 47 KB notebook copy and a CSV backup did not, while 60-byte files and the small epoch report did). The training then resumed from the older `last.ckpt` and redid the steps. Before stopping a pod, wait at least 10 to 15 minutes after the last write and run `sync`, and on the next pod check the times of `last.ckpt` and the newest epoch checkpoint before starting. Unverified guess: the volume uploads large files late.
- A resume-checkpoint write can fail on the network volume: at the end of epoch 3 of the first F1 run `os.fsync` raised `FileNotFoundError` inside `ResumeCheckpoint._save`, which ended the 3-hour run (the callbacks after it, including the epoch's `flat_epoch_N_object.ckpt`, did not run either). `_save` now tries three times and then skips the write with an error in the log; the run resumes from the previous `last.ckpt`. Stale `.last.ckpt.tmp.*.tmp` files (135 MB each) stay in `lightning_resume/` and can be deleted.
- The container may use fewer CPUs than `nproc` shows (13.6 of 128: `cat /sys/fs/cgroup/cpu.max`). torch's 128 threads throttled each other (a 16-clip probe took 490 s, 12 s with 8 threads): `cpu_threads.limit_threads()` runs in the entry points and the notebook sets `OMP_NUM_THREADS`; the 12 loader workers share the same quota. The Jupyter kernel's `MPLBACKEND` (`matplotlib_inline`) does not exist in the venv: the notebook sets `agg`.
- `py-spy` cannot attach inside the container (no ptrace); profile with `timeout -s INT 240 python -m cProfile -o out.prof ...` (the interrupt still writes the profile), then `pstats`. `sh(quiet=True)` in the notebook shows only the tail of a failing run, which can be one harmless traceback: `log=` keeps all of it in `LOGS/<log>.log`.
- The metrics CSV of a run is `spt/runs/<date>/<time>/<id>/metrics.csv` (stable-pretraining's logger, flushed every 100 logged steps; with `spt_dir` in the local folder named in `<run>/spt_location.txt`), not `lightning_logs/`; `analysis/plot_training.py` reads it. A symlink on the network volume cannot be read back (`OSError: [Errno 22]` from `Path.resolve()`): `local_spt_dir` first linked `<run>/spt` to the local folder (tested only on a Mac) and the first F1 start on RunPod failed with it; `spt_dir` is now used as `cache_dir` directly.
- Probe scores below zero mean too few samples for the latent dimension (`PROBE_FEW_SAMPLES`).
- Shell: zsh does not split unquoted variables; `timeout` is missing; `sleep` loops in the foreground are blocked, use `until ...; do sleep 5; done` as a background command; the safety check rejects `zsh -c "..."` wrappers, write a script file instead.
- A file collected before 2026-10-21 has no `action_policy` (the policy's choice in `action`): the collector refuses to append to it (column mismatch) until `relabel_asleep.py` has run; the flat notebook refuses to train on it.
- Collection: the collector appends and `--target-frames` counts the frames of one run, so a repeated run adds a full share on new seeds. `run.py` writes a marker `$HJEPA_HOME/collect_done/<job>` after each finished collect job (local and SLURM) and skips those; a killed run has none and starts again (its partial episodes stay).
- Expert training overrides need the `alg.` prefix on the command line (`alg.SAVE_PATH=...`, `alg.RESUME=true`): the group file's own value beats a top-level `SAVE_PATH=...`, which is silently ignored.
- Expert training: the chunked loop (`chunk_fn` in `pqn_rnn_craftax.py`) must keep the greedy test a real `lax.cond`: under `vmap` the state arrives batched, the cond becomes a select and the 10000-step test runs in every update (fixed for one seed, several seeds still do it; a test guards it). Time the expert with `purejaxql/scripts/time_expert.py` before choosing `TOTAL_TIMESTEPS`: the run length also sets the learning-rate and epsilon schedules and cannot be extended later.
- RunPod: the image's `LD_LIBRARY_PATH=/usr/local/cuda/lib64` (CUDA 12.8) makes JAX segfault at the first matmul next to the pip CUDA 12.9 libraries; run JAX without it (the notebook strips it). Seen on a pod with Python 3.12.
- GPU: `purejaxql[jax_envs]` alone installs the CPU jax on Linux; use `environment/jax-gpu-requirements.txt` (`jax[cuda12]==0.4.38`). Episodes collected on a GPU must pass `purejaxql/scripts/check_replay.py` on the CPU before anything is trained or planned on them. Never run the JAX tests with the python of `Craftax/.venv` (jax 0.11).
- `hjepa_forward` logs only metrics whose key contains `loss`, which is why some statistics are named `*_loss_levelN`.
