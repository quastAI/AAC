# Environments

Two Python projects with separate environments (JAX and PyTorch do not share one).

| Side | Install | Tests |
|---|---|---|
| JAX: expert, collector, analysis, experiments | `pip install -r environment/jax-requirements.txt` | `pytest purejaxql/tests analysis/tests experiments/tests` |
| PyTorch: H-JEPA | `pip install -r environment/hjepa-requirements.txt` (CPU torch: see the header of the file) | `cd H-JEPA && PYTHONPATH=. pytest tests` |

The `reference-freeze-*.txt` files list the exact versions of the environments the tests ran in (macOS arm64, Python 3.12). They are a record of what was known to work, not a cross-platform lock file: write a real lock for the cluster (`pip freeze` or `uv pip compile` on the target machine) when the first GPU runs start, and commit it here.

Pins that matter: `jax<=0.4.38` needs `flax<=0.10.3` (newer flax crashes with it), `craftax==1.6.1`, `torch==2.7.1`, `transformers==4.51.3` (a fresh resolve can pick a release that does not import with torch 2.7.1; the 153 tests passed with 4.51.3 on Python 3.11), `gymnasium==1.2.3`, `stable-pretraining==0.1.7`.

If `pip` points at a private index with expired credentials, use `PIP_INDEX_URL=https://pypi.org/simple` for a throwaway environment instead of changing the configuration.

## On a RunPod pod (A100, network volume at `/workspace`)

Nothing here has run on a GPU yet (written on macOS): check the first notebook run. The notebook [notebooks/runpod_dataset.ipynb](../notebooks/runpod_dataset.ipynb) does the JAX side of this (expert training, data collection) in one go, [notebooks/runpod_flat.ipynb](../notebooks/runpod_flat.ipynb) the PyTorch side (the flat model: training, probes, planning), and one notebook per variant (`runpod_V*_*.ipynb`) the variants; their helpers and pod paths are in `notebooks/pod.py`.

- **JAX (collector, expert):** `pip install -r environment/jax-gpu-requirements.txt` from the repository root, in its own venv. Without the `jax[cuda12]` pin the collector runs on the CPU. Check with `python -c "import jax; print(jax.devices())"`.
- **PyTorch (H-JEPA):** its own venv, `pip install -r environment/hjepa-requirements.txt` (torch 2.7.1 from PyPI is a CUDA 12 build; the image's own torch, probably 2.8, is not used). JAX in this venv is the CPU build on purpose: the planning environment pins `JAX_PLATFORMS=cpu` and must not compete with torch for the GPU. Python 3.11 is the project's pin; the RunPod pod I saw ran 3.12, for which JAX 0.4.38 has wheels.
- **`LD_LIBRARY_PATH`:** the RunPod image sets it to `/usr/local/cuda/lib64` (its own CUDA 12.8). JAX then loads that cuBLAS next to the pip-installed CUDA 12.9 libraries and crashes with a segmentation fault at the first matrix multiply. Run JAX processes without it (`env -u LD_LIBRARY_PATH ...`); the notebook does this for everything it starts.
- **Keep on the volume:** `HJEPA_HOME` (data, checkpoints, reports), the expert snapshots. Set `HJEPA_HOME=/workspace/data` and `HDF5_USE_FILE_LOCKING=FALSE` (HDF5 can fail to lock files on network volumes).
- **Not on the volume (seen on the first flat-model pod):** the network volume refuses `chmod` (`Operation not permitted`). `git clone` fails on it (`could not set 'core.filemode'`), and so does `python -m venv` (`ensurepip`, pip makes scripts executable). `runpod_flat.ipynb` keeps the clone (`/root/AAC`), the PyTorch venv (`/root/venvs/hjepa`) and the episode files (`/root/data`) on the pod's local disk: all three are made again on a new pod (clone by hand once per pod; the venv takes a few minutes, the 9 GB of data a minute or two). Checkpoints, reports and task files stay on the volume (`/workspace/data`, linked into `/root/data`); what is written at every logging step (the notebook's logs, stable-pretraining's folder via `spt_dir`) is on the local disk, because each logging step stalled the training about 10 s on the volume. The Hub download only warns on the volume (`Could not set the permissions`). The kernel's `MPLBACKEND` (`matplotlib_inline`) is not in the venv: the notebook sets `MPLBACKEND=agg` for what it starts.
- **CPU quota:** `nproc` shows the host's cores (128 on the first flat-model pod), the container may use far fewer (`cat /sys/fs/cgroup/cpu.max`: `1360000 100000` = 13.6 cores). torch then starts 128 threads that throttle each other: the probe's regressions took 490 s instead of 12 s (16 clips). The flat notebook sets `OMP_NUM_THREADS` and `MKL_NUM_THREADS` from the quota (at most 8); set them in anything else started by hand.
- **Dataloader:** the training config asks for `num_workers: 12`, `prefetch_factor: 8`, `persistent_workers`. The 12 workers share the CPU quota (about 13.6 cores on the pod above), so more workers do not help; the loader rate of `time_run.py --loader-batches` against the step rate says whether loading is the bottleneck. Check `df -h /dev/shm` too; with a small `/dev/shm` or few cores lower `loader.num_workers` and `loader.prefetch_factor`.
- **Data on local disk:** reading the training file from the network volume stalled the dataset build (more than 4 minutes without progress); with the files on the pod's local disk it takes 2 seconds, which is why the notebook downloads them to `/root/data`.
- **Cross-backend replay.** Episodes collected on the GPU must replay identically on the CPU planning environment (floating point differs between backends). `JAX_PLATFORMS=cpu python purejaxql/scripts/check_replay.py --data <file.h5>` replays a sample on the CPU and compares every column, the full state leaf by leaf (integer leaves exactly, the light level to 1e-6: on the first A100 collection it differed in the last bits from frame 2 on, with the game itself identical); the notebook runs it after the collection.
- **A restarted collection** skips the runs that finished (`$HJEPA_HOME/collect_done/`); a run that was killed starts again and its partial episodes stay in the file.
